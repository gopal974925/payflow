# PayFlow Microservices Architecture
*The wallet/payments backend split into independent services. Node.js, TypeScript, PostgreSQL, Redis, RabbitMQ (or Kafka), Docker.*

> **Simulation only.** Mock bank gateway, no real money or card data.

---

## 1. The Most Important Design Decision

Do **not** split wallets and the ledger into separate services. A P2P transfer must debit one wallet and credit another **atomically**. If those live in different services with different databases, you lose simple ACID transactions and need sagas for the core money path, which is risky and hard to reason about.

**Rule used here:** split by business capability, but keep everything that needs a single transaction (wallets + ledger + transfers) in one service. Use sagas only for flows that genuinely cross boundaries (top-up via bank, merchant payments).

This is also a strong interview answer: *"I didn't split blindly. I kept the consistency boundary intact."*

## 3. Services in Detail

### 3.1 API Gateway
- Single entry point for clients and merchants
- JWT verification (public key from Auth), rate limiting (Redis), request ID injection, routing, CORS
- Aggregates nothing complex. It routes and protects.
- **Tech:** Express/Fastify with `http-proxy-middleware`, or Kong/Nginx if you prefer

### 3.2 Auth & User Service
- Owns: users, credentials, PIN, sessions/refresh tokens, KYC-lite status, devices
- Endpoints: register, login, refresh, logout, set/verify PIN, profile
- Issues JWTs signed with a private key. Other services verify with the public key.
- Emits: `user.registered`, `user.pin_locked`
- **DB tables:** `users`, `refresh_tokens`, `devices`, `kyc_records`

### 3.3 Wallet & Ledger Service (the core)
- Owns: wallets, ledger entries, P2P transfers, balances, wallet limits, freezes
- Guarantees: atomic double-entry, row locks in ascending ID order, idempotency, `CHECK (balance >= 0)`
- Internal API (called by Payment Orchestrator): `debit`, `credit`, `transfer`, `reverse`, each idempotent
- Public via gateway: balance, statement, P2P transfer
- Uses the **transactional outbox** to emit events reliably
- Emits: `wallet.created`, `transfer.completed`, `transfer.failed`, `ledger.entry_posted`
- **DB tables:** `wallets`, `ledger_entries`, `transfers`, `idempotency_keys`, `outbox`

### 3.4 Payment Orchestrator Service
- Owns: top-ups, merchant payments, refunds, and the **saga state** for multi-step flows
- Coordinates Bank Gateway, Wallet & Ledger, and Merchant services
- Runs the payment state machine: `INITIATED -> PENDING -> SUCCESS / FAILED -> REVERSED`
- Handles compensation (e.g. bank succeeded but wallet credit failed -> retry, then reverse)
- Emits: `payment.initiated`, `payment.succeeded`, `payment.failed`, `refund.completed`
- **DB tables:** `payments`, `saga_instances`, `saga_steps`, `outbox`, `inbox`

### 3.5 Bank Gateway Service (mock)
- Simulates a bank/UPI switch: create order, random delay, success/fail, signed callback
- Sends HMAC-signed callbacks with retries and occasional duplicates or out-of-order events (to test your handling)
- Has its own database and API, as an external system would
- **DB tables:** `bank_orders`, `bank_callbacks`

### 3.6 Merchant Service
- Owns: merchant onboarding, API keys (hashed), webhook URLs and secrets, settlements
- Creates payment requests and QR payloads, then delegates the payment to the Orchestrator
- Emits: `merchant.created`, `settlement.generated`
- **DB tables:** `merchants`, `api_keys`, `payment_requests`, `settlements`

### 3.7 Notification Service
- Consumes `transfer.completed`, `payment.succeeded`, `user.pin_locked`, etc.
- Sends mock SMS/email/push (log to console or Mailhog)
- Deduplicates using an `inbox` table (event ID unique)
- **DB tables:** `notifications`, `templates`, `inbox`

### 3.8 Webhook Delivery Service
- Consumes `payment.*` events and delivers signed webhooks to merchant URLs
- Exponential backoff (1m, 5m, 30m, 2h), dead-letter queue, manual replay endpoint
- **DB tables:** `webhook_endpoints_cache`, `deliveries`, `attempts`

### 3.9 Fraud & Risk Service
- Consumes transfer and payment events, applies rules (velocity, amount spike, new device, ping-pong transfers)
- Produces risk flags, and can call Wallet & Ledger to freeze a wallet
- Start with pre-computed flags after the event. A real-time pre-check (synchronous, low latency) is an advanced upgrade.
- **DB tables:** `risk_rules`, `risk_flags`, `user_velocity_counters`

### 3.10 Reconciliation & Reporting Service
- Nightly job: verifies ledger sums, wallet balances, bank callbacks vs payments, and settlement totals
- Builds read-optimized statements and analytics from events (CQRS-style read model)
- **DB tables:** `recon_runs`, `mismatches`, `daily_summaries`

## 4. Communication Patterns

| Use | Style | Why |
|---|---|---|
| Client to gateway | REST/JSON | Standard |
| Orchestrator to Wallet/Ledger | gRPC or REST with idempotency keys | Needs an immediate answer |
| Orchestrator to Bank Gateway | REST | Simulates an external system |
| Everything else | Async events on the bus | Loose coupling, retries |

### Event catalog (versioned, with `event_id`, `type`, `version`, `occurred_at`, `correlation_id`, `payload`)

| Event | Producer | Consumers |
|---|---|---|
| `user.registered` | Auth | Wallet & Ledger (creates wallet), Notification |
| `wallet.created` | Wallet & Ledger | Reporting |
| `transfer.completed` | Wallet & Ledger | Notification, Fraud, Reporting |
| `payment.succeeded` / `payment.failed` | Orchestrator | Webhook, Notification, Merchant, Reporting |
| `refund.completed` | Orchestrator | Webhook, Notification |
| `risk.flag_raised` | Fraud | Wallet & Ledger (freeze), Notification |

### Reliability for messaging
- **Outbox** in every producer: write the event in the same DB transaction as the state change, then a relay publishes it
- **Inbox** in every consumer: store processed `event_id` and ignore duplicates (at-least-once delivery becomes effectively-once)
- Dead-letter queues and a replay tool
- Never depend on event order across aggregates. Use versions or timestamps to reject stale updates.

## 5. Key Flows

### 5.1 P2P transfer (single service, single transaction)
Client -> Gateway -> Wallet & Ledger. Lock both wallets in order, write two ledger entries, write an outbox event, commit. Then `transfer.completed` fans out to Notification, Fraud and Reporting. **No saga needed**, which is the payoff of the boundary choice.

### 5.2 Top-up via bank (saga, orchestrated)
1. Orchestrator creates a `payment` (`INITIATED`) and calls the Bank Gateway. State becomes `PENDING`.
2. Bank Gateway sends a signed callback to the Orchestrator. It verifies the signature and timestamp and dedupes by provider event ID.
3. On success, the Orchestrator calls Wallet & Ledger `credit` with the payment ID as the idempotency key. The system pool wallet is debited in the same call.
4. State becomes `SUCCESS` and `payment.succeeded` is published.
5. **If the credit call fails or times out:** retry with the same idempotency key. After N failures, mark `NEEDS_REVIEW` and raise an alert (money was taken by the bank but not credited, so never silently fail).

### 5.3 Merchant payment (saga)
1. Merchant Service creates a payment request. Customer approves with PIN (verified via Auth).
2. Orchestrator calls Wallet & Ledger `transfer` (customer to merchant wallet) with an idempotency key.
3. On success, `payment.succeeded` triggers the Webhook Delivery Service, which notifies the merchant.
4. **Refund:** Orchestrator calls `reverse` on Wallet & Ledger, which posts new reversing entries linked to the original.

### 5.4 Saga rules
- Use **orchestration** (Orchestrator holds the state), not choreography, for money flows. It is easier to debug and audit.
- Every step is idempotent. Every step has a defined compensation or a manual-review state.
- Persist saga state after every step so a crash resumes correctly.

## 6. Cross-Cutting Concerns

| Concern | Approach |
|---|---|
| **Auth between services** | Gateway verifies the user JWT. Internal calls use service tokens (signed JWT or mTLS) |
| **Tracing** | `X-Correlation-ID` created at the gateway and propagated in HTTP headers and event metadata. Add OpenTelemetry + Jaeger for a bonus |
| **Logging** | Structured JSON (pino) with correlation ID, shipped to console or Loki |
| **Metrics** | Prometheus + Grafana: request rate, p95 latency, queue depth, saga failures |
| **Resilience** | Timeouts on every call, retries with jitter, circuit breaker (opossum), bulkheads |
| **Config/secrets** | `.env` per service, shared via Docker Compose. Never commit secrets |
| **Contracts** | Shared `packages/contracts` with Zod schemas and event types, versioned |
| **API docs** | OpenAPI per service, aggregated at the gateway |
| **Health** | `/health/live` and `/health/ready` on every service |

## 8. Failure Scenarios to Design and Test

| Scenario | Expected behavior |
|---|---|
| Wallet service down during top-up callback | Orchestrator retries with the same idempotency key, and the state stays `PENDING` |
| Duplicate bank callback | Ignored via unique provider event ID |
| Event bus down when transfer commits | Outbox holds events, relay publishes after recovery |
| Notification service crashes mid-event | Message redelivered, inbox dedupes |
| Merchant webhook endpoint returns 500 | Retries with backoff, then dead-letter and replay |
| Orchestrator crashes mid-saga | Resumes from persisted saga state |
| Two transfers A->B and B->A concurrently | Lock ordering prevents deadlock |
| Fraud service slow or down | Money flow is unaffected (async, non-blocking) |

Write a test or a chaos script (`docker stop wallet-ledger`) for each row. This is what impresses interviewers.

- Reconciliation service, nightly job, mismatch reports

### Scope control
If time is short, merge **Notification + Webhook** into one service and **Fraud + Reconciliation** into one "Risk & Reporting" service. That gives **6 services**, which is still a valid microservices story and far more achievable.

Suggested minimum viable set (6): **Gateway, Auth, Wallet & Ledger, Payment Orchestrator (with mock bank module), Merchant, Notification/Webhook.**

## 10. Honest Trade-offs (say these in interviews)

- Microservices add network failures, distributed debugging, eventual consistency and deployment overhead. For a small team, a modular monolith is often the better choice.
- This project uses microservices to **demonstrate** service boundaries, sagas, outbox/inbox and observability.
- The one boundary I refused to split (wallet + ledger) is where consistency matters most.
- If asked "would you start with microservices in a real startup?", the strong answer is: *start with a modular monolith, split when team size or scaling needs justify it, and keep module boundaries clean so splitting is cheap.*
